# 19. TLB (Paging: Faster Translations)

> 페이징의 "너무 느림" 문제를 해결하는 주소 변환 캐시. 지역성으로 히트율을 얻고, 문맥 교환 시 플러시 또는 ASID 로 처리

- 원서 PDF — [19-Translation-Lookaside-Buffers.pdf](../../pdfs/01-virtualization/19-Translation-Lookaside-Buffers.pdf)
- 실습 — [[OS/ostep/projects/06-tlb-measure/README|실습 6. TLB 크기·비용 측정]]
- 원서 절 구조 — 19.1 기본 알고리즘 · 19.2 배열 접근 예 · 19.3 미스 처리 주체 · 19.4 TLB 내용 · 19.5 문맥 교환 · 19.6 교체 정책 · 19.7 실제 TLB 항목 · 19.8 요약

- 페이징을 가상 메모리의 핵심 기법으로 쓰면 **높은 성능 오버헤드**로 이어질 수 있음
- 주소 공간을 작은 고정 크기 단위로 쪼개므로 **많은 매핑 정보**가 필요하고, 그 정보가 물리 메모리에 저장되므로 프로그램이 생성하는 **가상 주소마다 추가 메모리 조회 1회**가 논리적으로 필요
- 모든 명령어 반입이나 명시적 `load`/`store` 전에 변환 정보를 위해 메모리에 가는 것은 **금지될 정도로 느림**

> [!question] CRUX: 주소 변환을 어떻게 빠르게 하는가
> 주소 변환을 어떻게 빠르게 하고, 페이징이 요구하는 듯한 추가 메모리 참조를 일반적으로 어떻게 피하는가. 어떤 하드웨어 지원이 필요한가. 어떤 OS 개입이 필요한가

- 해법 — **TLB(translation-lookaside buffer)**. 역사적 이유로 붙은 이름
- 실체 — 칩의 MMU 일부이며, **인기 있는 가상→물리 주소 변환의 하드웨어 캐시**. 더 나은 이름은 **주소 변환 캐시(address-translation cache)**
- 동작 — 가상 메모리 참조마다 하드웨어가 **먼저 TLB를 확인**. 원하는 변환이 있으면 페이지 테이블을 참조하지 않고 (빠르게) 변환 수행
- 엄청난 성능 영향 때문에 **TLB 는 실질적으로 가상 메모리를 가능하게 만듦**

## 19.1 기본 알고리즘

선형 페이지 테이블과 **하드웨어 관리 TLB** 가정.

```c
VPN = (VirtualAddress & VPN_MASK) >> SHIFT
(Success, TlbEntry) = TLB_Lookup(VPN)
if (Success == True)   // TLB Hit
    if (CanAccess(TlbEntry.ProtectBits) == True)
        Offset   = VirtualAddress & OFFSET_MASK
        PhysAddr = (TlbEntry.PFN << SHIFT) | Offset
        Register = AccessMemory(PhysAddr)
    else
        RaiseException(PROTECTION_FAULT)
else                   // TLB Miss
    PTEAddr = PTBR + (VPN * sizeof(PTE))
    PTE = AccessMemory(PTEAddr)
    if (PTE.Valid == False)
        RaiseException(SEGMENTATION_FAULT)
    else if (CanAccess(PTE.ProtectBits) == False)
        RaiseException(PROTECTION_FAULT)
    else
        TLB_Insert(VPN, PTE.PFN, PTE.ProtectBits)
        RetryInstruction()
```

| 경로 | 동작 |
|---|---|
| **TLB 히트** | 해당 TLB 항목에서 PFN 을 뽑아 원래 가상 주소의 오프셋과 이어붙여 물리 주소를 만들고 메모리 접근 (보호 검사 통과 전제) |
| **TLB 미스** | 하드웨어가 **페이지 테이블에 접근**해 변환을 찾고, 유효·접근 가능하면 **TLB를 갱신**한 뒤 **명령어를 재시도**(`RetryInstruction`) → 이번에는 TLB 히트 |

- 미스가 비싼 주된 이유 — **페이지 테이블 접근을 위한 추가 메모리 참조**
- TLB는 모든 캐시와 마찬가지로 **일반적 경우에 변환이 캐시에서 발견된다는 전제** 위에 구축
- 미스가 자주 일어나면 프로그램이 뚜렷하게 느려짐 — 메모리 접근은 대부분 CPU 명령어에 비해 상당히 비싸고, TLB 미스는 메모리 접근을 더 유발

## 19.2 예제 — 배열 접근

- 가정 — 4바이트 정수 10개 배열이 **가상 주소 100**에서 시작. **8비트 가상 주소 공간**, **16바이트 페이지** → VPN 4비트(가상 페이지 16개), 오프셋 4비트

배열 배치 (검산).

```text
        offset:  00      04      08      12
VPN = 06                a[0]    a[1]    a[2]      (페이지 6 = 96~111)
VPN = 07        a[3]    a[4]    a[5]    a[6]      (페이지 7 = 112~127)
VPN = 08        a[7]    a[8]    a[9]              (페이지 8 = 128~143)
```

```text
a[0] 주소 100 → 100 / 16 = 6.25 → VPN 6, offset 4  ✓
페이지 6 은 96~111 → 100, 104, 108 = a[0], a[1], a[2] 3개만 수용
a[3] 주소 112 → VPN 7 (112~127) → 112, 116, 120, 124 = a[3]~a[6] 4개
a[7] 주소 128 → VPN 8 → 128, 132, 136 = a[7]~a[9] 3개
```

접근 루프.

```c
int i, sum = 0;
for (i = 0; i < 10; i++) {
    sum += a[i];
}
```

### TLB 활동 추적

| 접근 | VPN | 결과 | 근거 |
|---|---|---|---|
| `a[0]` | 6 | **miss** | 배열 첫 접근 |
| `a[1]` | 6 | hit | `a[0]` 과 같은 페이지 |
| `a[2]` | 6 | hit | 같은 페이지 |
| `a[3]` | 7 | **miss** | 새 페이지 |
| `a[4]` | 7 | hit | |
| `a[5]` | 7 | hit | |
| `a[6]` | 7 | hit | |
| `a[7]` | 8 | **miss** | 새 페이지 |
| `a[8]` | 8 | hit | |
| `a[9]` | 8 | hit | |

```text
히트율 = 7 / 10 = 70%
```

- 프로그램이 배열에 처음 접근하는데도 TLB가 성능을 개선 — **공간 지역성(spatial locality)** 덕분. 배열 원소들이 페이지에 촘촘히 담겨 있어 **페이지의 첫 접근만 미스**
- **페이지 크기의 역할** — 페이지가 2배(32바이트)였다면 미스가 더 줄었을 것. 전형적 페이지 크기가 4KB 수준이므로 이런 밀집 배열 접근은 **페이지당 미스 1회**로 훌륭한 TLB 성능
- 루프 완료 직후 배열에 다시 접근하면 (TLB가 충분히 크면) **hit ×10** → **시간 지역성(temporal locality)** 덕분

> [!tip] TIP: 가능하면 캐싱을 사용할 것
> 캐싱은 컴퓨터 시스템에서 **가장 근본적인 성능 기법** 중 하나 — "일반적 경우를 빠르게" 만드는 데 반복 사용됨.
> **시간 지역성** — 최근 접근된 명령어·데이터가 가까운 미래에 다시 접근될 가능성이 높음. 루프 변수나 루프 내 명령어
> **공간 지역성** — 주소 `x` 에 접근하면 `x` 근처에도 곧 접근할 가능성이 높음. 배열 순회
> 이 성질들은 프로그램의 정확한 성격에 의존하므로 **엄격한 법칙이 아니라 경험 규칙**.
> **캐시가 그렇게 좋다면 왜 더 크게 만들어 모든 데이터를 담지 않는가** — 물리 법칙에 부딪힘. **빠른 캐시는 작아야 함**(빛의 속도 등 물리 제약). 정의상 큰 캐시는 느리므로 목적을 잃음 → **작고 빠른 캐시를 어떻게 최대한 잘 쓸 것인가**가 남는 문제

## 19.3 TLB 미스는 누가 처리하는가

| 방식 | 시대·아키텍처 | 동작 |
|---|---|---|
| **하드웨어 관리** | 옛 CISC. **Intel x86** (고정 멀티 레벨 페이지 테이블, 현재 페이지 테이블은 **CR3 레지스터**가 지시) | 하드웨어가 페이지 테이블 위치와 **정확한 형식**을 알아야 함. 미스 시 하드웨어가 페이지 테이블을 **"걸어(walk)"** 올바른 PTE를 찾아 변환을 뽑고 TLB를 갱신한 뒤 명령어 재시도 |
| **소프트웨어 관리** | 현대 RISC. **MIPS R10k**, **Sun SPARC v9** | 미스 시 하드웨어가 **그냥 예외를 발생**. 현재 명령어 흐름을 멈추고 특권 수준을 커널 모드로 올리고 트랩 핸들러로 점프. OS 코드가 페이지 테이블에서 변환을 찾고 **특권 명령**으로 TLB를 갱신한 뒤 트랩에서 복귀 |

소프트웨어 관리 방식의 제어 흐름 (미스 부분만 다름).

```c
...
else   // TLB Miss
    RaiseException(TLB_MISS)
```

### 소프트웨어 관리의 두 가지 중요 세부

1. **return-from-trap 이 시스템 콜 때와 달라야 함**
   - 시스템 콜 복귀 — 트랩 **다음 명령어**에서 실행 재개 (프로시저 호출 복귀와 같은 방식)
   - **TLB 미스 처리 복귀** — **트랩을 유발한 그 명령어**에서 재개해야 함. 재시도가 이번에는 TLB 히트를 내게 함
   - 따라서 **트랩·예외 원인에 따라 하드웨어가 다른 PC를 저장**해야 함
2. **무한 TLB 미스 연쇄를 피해야 함**
   - TLB 미스 처리 코드 자체가 TLB 미스를 유발하면 무한 연쇄
   - 해법 — TLB 미스 핸들러를 **물리 메모리에 두어**(매핑되지 않고 주소 변환 대상이 아님), 또는 TLB의 일부 항목을 **영구 유효 변환용으로 예약**해 핸들러 코드에 사용. 이런 **고정(wired) 변환**은 항상 TLB에 히트

### 소프트웨어 관리의 장점

| 장점 | 내용 |
|---|---|
| **유연성** | OS가 **원하는 어떤 자료 구조로도** 페이지 테이블을 구현 가능. **하드웨어 변경 불필요** |
| **단순성** | 하드웨어가 미스 시 하는 일이 적음 — **예외만 발생**시키고 나머지는 OS 핸들러가 처리 |

> [!note] ASIDE: RISC vs CISC
> 1980년대 컴퓨터 아키텍처 학계의 큰 논쟁. **CISC**(Complex Instruction Set Computing) 진영 대 **RISC**(Reduced Instruction Set Computing) 진영. RISC 는 Berkeley 의 David Patterson 과 Stanford 의 John Hennessy 가 주도.
> - **CISC** — 명령어가 많고 각각 상대적으로 강력. 예: 포인터 2개와 길이를 받아 바이트를 복사하는 문자열 복사. 착상 — 명령어가 고수준 프리미티브여야 어셈블리 사용이 쉽고 코드가 간결
> - **RISC** — 정반대. 핵심 관찰은 **명령어 집합이 실제로는 컴파일러의 목표물**이라는 것. 컴파일러가 원하는 것은 고성능 코드를 만들 수 있는 **단순한 프리미티브 몇 개**뿐 → 하드웨어에서 최대한(특히 마이크로코드) 걷어내고 남은 것을 단순·균일·빠르게
> 초기에 RISC 칩이 뚜렷하게 빨라 큰 영향. 그러나 시간이 지나며 Intel 같은 CISC 제조사가 **RISC 기법을 코어에 통합**(복잡 명령을 마이크로 명령으로 변환하는 초기 파이프라인 단계 추가) + 트랜지스터 증가로 CISC 도 경쟁력 유지. 오늘날 두 유형 모두 빠르게 만들 수 있어 논쟁은 가라앉음

## 19.4 TLB 에는 무엇이 있는가

- 전형적 TLB — **32·64·128 항목**, **완전 연관(fully associative)**
  - 완전 연관 = 어떤 변환이든 TLB 어디에나 있을 수 있고, 하드웨어가 **전체 TLB를 병렬 탐색**

```text
┌───────┬───────┬─────────────┐
│  VPN  │  PFN  │ other bits  │
└───────┴───────┴─────────────┘
```

- **VPN 과 PFN 이 모두 각 항목에 존재** — 변환이 어느 위치에든 들어갈 수 있으므로

| other bits | 역할 |
|---|---|
| **valid** | 이 항목에 유효한 변환이 있는지 |
| **protection** | 페이지에 어떻게 접근할 수 있는지. 코드 페이지는 읽기·실행, 힙 페이지는 읽기·쓰기 등 |
| **ASID** | 주소 공간 식별자 (아래) |
| **dirty** | 수정 여부 |

> [!note] ASIDE: TLB valid 비트 ≠ 페이지 테이블 valid 비트
> 흔한 혼동.
> **페이지 테이블의 PTE valid 비트** — 그 페이지가 **프로세스에 의해 할당되지 않았음**을 의미. 올바르게 동작하는 프로그램이 접근해서는 안 되는 것. 무효 페이지 접근의 통상 대응은 **OS로 트랩 → 프로세스 종료**
> **TLB valid 비트** — 단순히 **그 TLB 항목에 유효한 변환이 들어 있는지**만 가리킴. 시스템 부팅 시 각 TLB 항목의 통상 초기 상태는 무효(캐시된 변환이 아직 없으므로). 가상 메모리가 활성화되고 프로그램이 주소 공간에 접근하기 시작하면 TLB가 천천히 채워짐
> TLB valid 비트는 **문맥 교환 시에도 유용** — 모든 항목을 무효로 설정하면 곧 실행될 프로세스가 **이전 프로세스의 변환을 실수로 쓰는 것을 방지**

## 19.5 문제 — 문맥 교환

- TLB 는 **현재 실행 프로세스에만 유효한** 가상→물리 변환을 담음. 다른 프로세스에는 무의미
- 프로세스 P1 의 10번째 가상 페이지가 물리 프레임 100 에, P2 의 10번째 가상 페이지가 물리 프레임 170 에 매핑된 경우.

| VPN | PFN | valid | prot |
|---|---|---|---|
| 10 | 100 | 1 | rwx |
| — | — | 0 | — |
| 10 | 170 | 1 | rwx |
| — | — | 0 | — |

- **문제** — VPN 10 이 PFN 100(P1)으로도, PFN 170(P2)으로도 변환되는데 **하드웨어가 어느 항목이 어느 프로세스용인지 구별할 수 없음**

> [!question] CRUX: 문맥 교환 시 TLB 내용을 어떻게 관리하는가
> 프로세스 간 문맥 교환 시, 이전 프로세스에 대한 TLB 변환은 곧 실행될 프로세스에 무의미. 하드웨어 또는 OS 는 이 문제를 어떻게 해결해야 하는가

### 해법 1 — 플러시(flush)

- 문맥 교환 시 TLB를 **비움**. **모든 valid 비트를 0 으로** 설정
- 구현 — 소프트웨어 기반 시스템은 명시적(특권) 하드웨어 명령. 하드웨어 관리 TLB 는 **페이지 테이블 베이스 레지스터가 변경될 때** 플러시 실행 가능(OS는 문맥 교환 시 PTBR 을 어차피 바꿔야 함)
- **비용** — 프로세스가 실행될 때마다 자기 데이터·코드 페이지를 만지며 **TLB 미스를 감수**해야 함. OS가 프로세스를 자주 전환하면 이 비용이 높을 수 있음

### 해법 2 — ASID (address space identifier)

- 일부 하드웨어가 TLB 에 **ASID 필드** 제공. **PID 로 생각하면 되나 비트 수가 적음**(예: ASID 8비트 vs PID 32비트)

| VPN | PFN | valid | prot | **ASID** |
|---|---|---|---|---|
| 10 | 100 | 1 | rwx | **1** |
| — | — | 0 | — | — |
| 10 | 170 | 1 | rwx | **2** |
| — | — | 0 | — | — |

- ASID 로 **여러 프로세스의 변환을 동시에 보유**하면서 혼동이 없음
- 하드웨어가 현재 실행 프로세스를 알아야 하므로, OS는 **문맥 교환 시 특권 레지스터에 현재 프로세스의 ASID 를 설정**해야 함

### 페이지 공유

두 프로세스의 **다른 VPN 이 같은 물리 페이지**를 가리키는 경우.

| VPN | PFN | valid | prot | ASID |
|---|---|---|---|---|
| 10 | 101 | 1 | r-x | 1 |
| — | — | 0 | — | — |
| 50 | 101 | 1 | r-x | 2 |
| — | — | 0 | — | — |

- 두 프로세스가 **페이지를 공유**하는 경우(예: 코드 페이지). P1 은 자기 주소 공간 10번 페이지에, P2 는 50번 페이지에 매핑
- **코드 페이지 공유**(바이너리, 공유 라이브러리)는 **사용 중 물리 페이지 수를 줄여** 메모리 오버헤드 감소에 유용
- `prot` 이 `r-x`(읽기·실행, 쓰기 불가)인 점에 유의 — 공유가 안전한 근거

## 19.6 문제 — 교체 정책

> [!question] CRUX: TLB 교체 정책을 어떻게 설계하는가
> 새 TLB 항목을 추가할 때 어느 항목을 교체해야 하는가. 목표는 미스율 최소화(히트율 향상)와 성능 개선

| 정책 | 방법 | 특징 |
|---|---|---|
| **LRU (least-recently-used)** | 가장 오래 안 쓴 항목을 축출 | 메모리 참조 흐름의 지역성 활용. **최악 사례 존재** — 크기 `n` 인 TLB 에서 프로그램이 `n+1` 페이지를 루프하면 **매 접근이 미스** |
| **무작위(random)** | 임의 매핑을 축출 | **단순성**과 **코너 케이스 회피** 능력. 위 `n+1` 루프에서 LRU 보다 훨씬 나음 |

## 19.7 실제 TLB 항목 — MIPS R4000

소프트웨어 관리 TLB 를 쓰는 현대 시스템.

```text
┌──────────────────────┬─────────────────────┬───┬──────┬───┬─┬─┬─┐
│         VPN          │        PFN          │ G │ ASID │ C │D│V│ │
│      (19 bits)       │     (24 bits)       │   │(8bit)│(3)│ │ │ │
└──────────────────────┴─────────────────────┴───┴──────┴───┴─┴─┴─┘
```

| 필드 | 값·역할 |
|---|---|
| **VPN** | **19비트**. 32비트 주소 공간·4KB 페이지면 20비트를 기대하나, **사용자 주소는 주소 공간의 절반에서만** 오므로(나머지는 커널 예약) 19비트로 충분 |
| **PFN** | 최대 **24비트** → 최대 **64GB 물리 메모리** 지원 (`2^24 × 4KB`) |
| **G (global)** | 프로세스 간 **전역 공유** 페이지용. 설정되면 **ASID 는 무시** |
| **ASID** | **8비트**. OS가 주소 공간을 구별하는 데 사용 |
| **C (coherence)** | **3비트**. 페이지가 하드웨어에 의해 어떻게 캐시되는지 결정 |
| **D (dirty)** | 페이지에 쓰기가 있었으면 표시 |
| **V (valid)** | 항목에 유효한 변환이 있는지 |
| **page mask** (그림 생략) | **다중 페이지 크기** 지원 |

> [!question] 원서가 남긴 질문
> ASID 가 8비트(2^8 = 256)인데, **동시에 256개 넘는 프로세스**가 실행되면 OS는 무엇을 해야 하는가

- MIPS TLB 는 통상 **32 또는 64 항목**. 대부분 사용자 프로세스가 사용하되 **일부는 OS 예약**
  - **wired 레지스터**로 OS가 하드웨어에 몇 개 슬롯을 예약할지 알림. TLB 미스가 문제가 되는 임계 시점(예: TLB 미스 핸들러 안)에 접근할 코드·데이터에 사용
- 소프트웨어 관리이므로 **TLB 갱신 명령** 필요. MIPS 는 4개 제공

| 명령 | 동작 |
|---|---|
| `TLBP` | 특정 변환이 TLB 에 있는지 **탐사(probe)** |
| `TLBR` | TLB 항목 내용을 레지스터로 **읽음** |
| `TLBWI` | **특정** TLB 항목을 교체 |
| `TLBWR` | **무작위** TLB 항목을 교체 |

- 이 명령들이 **특권 명령**인 것이 결정적으로 중요 — 사용자 프로세스가 TLB 내용을 수정할 수 있다면 머신 장악, 자체 악성 "OS" 실행 등 거의 무엇이든 가능

## 19.8 정리

- 작고 전용인 온칩 TLB 를 **주소 변환 캐시**로 제공하면 대부분 메모리 참조가 **주 메모리의 페이지 테이블에 접근하지 않고** 처리됨
- 일반적 경우 프로그램 성능이 **메모리가 가상화되지 않은 것과 거의 같아짐** — OS의 훌륭한 성취이며 현대 시스템에서 페이징 사용에 필수적

### TLB 커버리지 초과

- 프로그램이 **짧은 기간에 접근하는 페이지 수가 TLB 에 들어가는 페이지 수를 넘으면** 많은 TLB 미스 발생 → 상당히 느려짐. 이를 **TLB 커버리지 초과(exceeding the TLB coverage)** 라 함
- 해법 하나 — **더 큰 페이지 크기 지원**. 핵심 자료 구조를 큰 페이지로 매핑되는 영역에 두면 **TLB 실효 커버리지 증가**
- 큰 페이지 지원은 **DBMS** 같은 프로그램이 자주 활용 — 크고 무작위 접근되는 자료 구조를 가짐

### TLB 와 CPU 파이프라인

- TLB 접근이 CPU 파이프라인의 **병목**이 되기 쉬움. 특히 **물리 인덱스 캐시(physically-indexed cache)** 에서 — 캐시 접근 전에 주소 변환이 끝나야 하므로
- 그래서 **가상 주소로 캐시에 접근**하는 여러 영리한 방법이 연구됨 — **가상 인덱스 캐시(virtually-indexed cache)**. 일부 성능 문제를 해결하나 하드웨어 설계에 새 문제를 도입

### macOS arm64 실측 요약

직접 측정한 결과 (상세는 [[OS/ostep/projects/06-tlb-measure/README|실습 6]]).

| 만지는 페이지 수 | 접근당 시간 | 해석 |
|---|---|---|
| 1~8 | **0.2~0.8 ns** | TLB·캐시 모두 히트 + 비순차 실행으로 병렬 처리 |
| 9~30 | **1.0 → 18 ns 로 선형 증가** | 8~9 사이에 첫 경계. 원서가 기대한 "계단"이 아니라 **경사** |
| 31~48 | 18 → 3.5 ns 로 **하락** | 하드웨어 프리페처 개입 추정 (확인 필요) |
| 56~8192 | **5.4~6.1 ns 로 평탄** | 정상 상태 |

- **구간 A 대비 구간 B 끝의 차이가 약 60배** → Culler 의 법칙("RAM 은 항상 RAM 이 아니다")의 직접 증거
- 원서가 기대한 **단일 계단이 나타나지 않는 이유** — 다단 TLB(L1 dTLB + L2 TLB), 하드웨어 프리페처, 비순차 실행, 비대칭 코어. 현대 하드웨어는 원서 모델보다 여러 층이 겹쳐 있음

> [!tip] TIP: RAM 은 항상 RAM 이 아니다 (Culler의 법칙)
> **random-access memory** 라는 용어는 어느 부분이든 똑같이 빠르게 접근할 수 있다는 뜻을 함축. 일반적으로 RAM 을 그렇게 생각하는 것이 좋으나, **TLB 같은 하드웨어·OS 기능** 때문에 특정 메모리 페이지 접근은 비쌀 수 있음 — 특히 그 페이지가 현재 TLB 에 매핑되어 있지 않으면.
> 주소 공간을 무작위로 접근하는 것, 특히 **접근 페이지 수가 TLB 커버리지를 넘으면** 심각한 성능 저하로 이어질 수 있음.
> 원서 저자들의 지도교수 David Culler 가 TLB 를 많은 성능 문제의 원천으로 늘 지적했기에 그의 이름을 붙임
